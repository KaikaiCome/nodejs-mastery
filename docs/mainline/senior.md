# 进阶：从主线项目到资深全栈

> 本章没有新代码，而是把主线项目当作“基线”，列出走向生产与资深所需的演进方向。每一项都可以作为独立的毕业项目选题。

## 1. 本项目刻意做的简化

| 简化 | 生产中的做法 | 你需要学会的 |
| --- | --- | --- |
| `node:sqlite` 单文件数据库 | PostgreSQL + 连接池 | 隔离级别、`SELECT ... FOR UPDATE`、`SKIP LOCKED`、慢查询分析（`EXPLAIN ANALYZE`）、在线迁移（expand/contract） |
| 内存会话与登录限流 | Redis | TTL、原子操作（`INCR` + `EXPIRE` / Lua）、Redis 故障时的降级策略 |
| HTTP 轮询投递 outbox | Kafka / RabbitMQ / CDC | 分区与顺序、消费者组、重平衡、死信队列 |
| 共享 service token | mTLS / 短期 JWT / 服务网格 | 证书轮换、零信任、最小权限 |
| 推荐服务无鉴权 | 网关统一鉴权 | 网关 vs 服务内鉴权的权衡 |
| 单实例 relay | 租约 / 领导者选举 | 时钟漂移、脑裂、fencing token |
| 手写日志与指标 | OpenTelemetry + Prometheus + Grafana + Loki | 采样、基数控制、SLO 与错误预算 |
| 本地进程 | 容器 + K8s | 探针、资源限制、HPA、滚动发布、PDB |

## 2. 推荐的演进路线（任选其一作为毕业项目）

1. **迁移到 PostgreSQL**：用 `pg` 替换 `lib/db.js`，保持所有测试通过（测试用 testcontainers 或 docker compose 启动数据库）。重写超卖实验，比较“条件更新”“`FOR UPDATE`”“`SERIALIZABLE` + 重试”三种策略的吞吐与正确性。
2. **多实例部署**：BFF 起 3 个实例放在 nginx 后面；会话与限流迁移到 Redis；relay 用 `SKIP LOCKED` 支持多实例；写一个测试证明任一实例被 kill 后用户无感知。
3. **引入消息队列**：outbox → Kafka（或 Redis Streams），通知服务成为消费者组；实现按 `orderId` 分区保序与死信队列；故障注入：消费者处理中途崩溃。
4. **可观测性落地**：接入 OpenTelemetry，在 Jaeger 中看到一次下单跨四个服务的完整 trace；定义 2 个 SLO（如“下单成功率 99.9%”“首页 P99 < 500ms”）与对应的燃烧率告警。
5. **前端工程化**：用 React/Vue + TypeScript 重写 `web/`，接入 SSR（Next/Nuxt）或保持 SPA；从 OpenAPI 生成类型安全的客户端；Playwright 端到端测试覆盖“下单 → 支付 → 通知”。

## 3. 资深工程师的工作方式

技术点可以从文档中学到，下面这些只能靠刻意练习：

### 写设计文档与 ADR

每个重要决策写一份简短的 ADR（Architecture Decision Record）：

```markdown
# ADR-003：订单事件使用 Outbox 而非直接调用通知服务
## 背景      下单后需要通知；直接调用存在双写问题……
## 决策      同事务写 outbox 表，后台 relay 投递，消费者 inbox 去重
## 备选方案  ① 直接调用 + 重试 ② 2PC ③ CDC（Debezium）
## 后果      + 不丢事件；不拖慢下单  − 至少一次，消费者必须幂等；投递有延迟
```

练习：为本项目的 5 个关键决策（同步 SQLite、条件更新防超卖、BFF 同源、内存会话、外壳自研而非 Express）各写一份 ADR，并说明**在什么条件下应该推翻它**。

### 容量估算

在动手之前先算：

```text
日活 10 万，人均 20 次页面请求，高峰系数 5
≈ 100000 × 20 / 86400 × 5 ≈ 115 QPS（高峰）
首页一次请求 = 3 个下游调用 → 下游约 350 QPS
单实例压测 1500 RPS（见运维章节）→ 2 个实例即可，3 个实例保证一台故障时仍有余量
```

能做出这样的估算，并用压测数据验证，才能回答“需要几台机器”“瓶颈在哪里”。

### 故障复盘

每次出问题都写复盘（Postmortem）：时间线、影响范围、根因（5 个为什么）、**改进项及负责人**。不追责，只改系统。可以用本项目的“破坏实验”模拟一次故障并写复盘作为练习。

### 评审他人代码

读完主线项目后，挑出你认为最弱的 3 处设计并给出改进方案。本项目已知的弱点包括：relay 单实例假设、会话不跨实例、推荐服务无鉴权、幂等重放返回订单当前状态（而非首次响应）。你能找到更多吗？
