# 前端到后端的思维转变

前端代码跑在**用户的**机器上，一个用户一个进程，出错影响一个人；后端代码跑在**你的**机器上，一个进程服务成千上万的请求，出错影响所有人。几乎所有后端思维都源于这个差异。

## 七个关键转变

| 维度 | 前端习惯 | 后端要求 |
| --- | --- | --- |
| 状态 | 组件内存状态随意用 | 进程是**无状态**的，状态放 DB/Redis；进程随时可能被杀、被扩容 |
| 错误 | 报错刷新即可 | 一个未捕获异常可能让进程退出，所有在途请求失败 |
| 性能 | 关注首屏、渲染 | 关注吞吐（QPS）、延迟分位（P99）、资源（CPU/内存/连接数） |
| 并发 | 单用户，少竞争 | 同一数据被并发修改：需要锁、事务、幂等 |
| 信任 | 信任自己的 UI | **永不信任输入**：校验、鉴权、限流 |
| 时间 | 一次会话几分钟 | 进程运行数周，微小泄漏会累积成 OOM |
| 可见性 | DevTools 直接看 | 只能靠日志、指标、链路追踪“远程看病” |

## 写每个接口前问自己的 10 个问题

1. 输入合法吗？谁可以调？（校验、鉴权、越权）
2. 下游慢了/挂了怎么办？（超时、重试、降级）
3. 被重复调用会怎样？（幂等）
4. 两个请求同时改同一数据会怎样？（并发控制）
5. 数据量涨 100 倍还能跑吗？（分页、索引、流式）
6. 出了问题我怎么知道？（日志、指标、告警）
7. 出了问题我怎么定位？（traceId、上下文日志）
8. 失败时返回什么？（错误码规范、不泄露内部信息）
9. 能不能平滑上线/回滚？（兼容性、开关、灰度）
10. 有没有更简单的方案？（避免过度设计）
